# 정책 기반 게이트웨이 적용 상세 설명

2026-11-03. 설계 기준은 [구현 계획](POLICY_GATEWAY_IMPLEMENTATION_PLAN.md)입니다. 현재 단계는 가상 데이터로 기능을 구현·검증한 프로젝트이며 사내 운영 배포 완료를 뜻하지 않습니다. 이번 작업은 GitHub 푸시 준비까지만 수행합니다.

## 1. 달라진 요청 흐름

이전에는 유효한 DB 읽기 요청도 건별로 사람 승인을 받아야 했습니다. 이제 보안 에이전트가 규칙으로 분석하고, 게이트웨이가 명시적인 권한 정책에 따라 다음 중 하나를 결정합니다.

| 접수 결과 | 조건 | 다음 동작 |
|---|---|---|
| 자동 허용, HTTP 200 | 등록된 기본 조회 정책 또는 유효한 반복 업무 승인에 일치 | 원래 요청 에이전트가 execute API 호출 |
| 승인 대기, HTTP 202 | 권한상 가능한 요청이지만 자동 허용 범위 밖 | 사람이 근거를 검토하고 일회 또는 제한된 반복 승인 |
| 차단, HTTP 403 | 미등록 열, 테넌트·역할 위반, 잘못된 형식, 분석 실패 등 | 실행 불가. 사람이 덮어써서 허용할 수 없음 |

‘정책결정’은 요청을 허용·검토·차단하는 게이트웨이의 접근통제 결정을 뜻합니다. LLM의 자유로운 판단이나 침해 확률이 아닙니다. 요청 접수의 허용은 SQL 실행 완료가 아니며, 원래 에이전트의 별도 실행 단계에서 다시 검증합니다.

## 2. LLM을 제거한 범위

LLM 어댑터, Ollama 호출 경로, 입력 의미 분류기, 학습형 n-gram 분류기, 모델 JSON, 해당 테스트·학습·외부 평가 실행기 등 **26개 파일을 제거**했습니다. [삭제 목록](../testing/LLM_REMOVAL_MANIFEST.md)에 정확한 경로를 남겼습니다. 새 실행파일도 현재 소스로 다시 만들었습니다.

현재 `security_agent/assessment.py`는 카탈로그·민감 열·대량 요청·요청 빈도 등 설명 가능한 조건을 분석합니다. `gateway/app/db_policy.py`가 허용 정책과 누적 한도를 적용합니다. 결정적 API 클라이언트는 유지하므로 요청자가 일반 프로그램이든 외부 AI 에이전트이든 동일한 구조화된 API를 사용합니다.

과거 평가 결과는 역사적 자료라는 표시와 함께 보존했습니다. 이를 현재 성능 주장에 사용하지 않습니다. 컴퓨터에 설치된 다른 프로그램과 기존 검증 DB·감사 기록은 삭제하지 않았습니다.

## 3. 사람 승인량을 줄이는 명시적 자동 정책

정책 원본은 `config/db_access.json`입니다. 기본 정책 `operations-basic-v1`은 다음 조건을 모두 요구합니다.

- 데이터: 운영 지원 이력 `operations`.
- 열: `ticket_id`, `category`, `status`의 일부 또는 전부. 자유문장 `description`은 제외.
- 서버에 등록된 역할과 작업 ID에 일치.
- 요청당 100행 이하이며 새 이상 징후가 없음.

점수가 낮다는 이유만으로 자동 허용하지 않습니다. 예를 들어 description 조회는 위험 점수가 낮아도 검토 대상으로 남습니다. 명시적 자동 정책이 없으면 유효한 요청도 사람에게 전달합니다. 승인 대기열이 가득 차도 자동 정책에 일치하는 기본 조회는 별도로 처리되는 것을 테스트했습니다.

민감정보·대량 조회는 기본 자동 정책에서 제외합니다. 사람이 업무 범위를 확인한 뒤 아래의 반복 승인을 발급할 수 있습니다. 과도한 빈도나 정책 위반은 승인 재사용으로 우회하지 못합니다.

## 4. 제한된 반복 업무 승인

승인 검토의 요청 보고서에서 ‘일회 승인’ 또는 ‘반복 업무 승인’을 선택합니다. 반복 승인은 기간·횟수·누적 반환 행 수를 함께 정해야 합니다.

| 항목 | 화면 제안값 | 서버가 허용하는 최대값 |
|---|---:|---:|
| 유효 기간 | 10분 | 1시간 |
| 실행 횟수 | 20회 | 100회 |
| 총 반환 행 수 | 2,000행 | 10,000행 |

최소 유효 기간은 60초입니다. 총량은 원래 요청의 최대 행 수 이상이어야 하며 **원래 승인한 요청의 실행도 한도에 포함**합니다. 실제 발급은 검토자가 선택한 값으로 제한됩니다.

재사용 범위는 신원·사용자·역할·테넌트·작업·DB 대상·데이터셋·열·필터·목적에 묶습니다. 요청당 최대 행 수는 줄일 수 있지만 늘릴 수 없습니다. 목적 문자열의 일치는 업무 목적의 진실성 검증을 뜻하지 않습니다. 역할·정책·대상 변경, 만료, 취소, 횟수·행 수 소진을 다시 검사합니다.

승인 검토 하단에서 최근 100개 반복 승인의 상태·기간·사용량을 보고 근거를 입력해 취소할 수 있습니다. 취소는 새 실행뿐 아니라 같은 승인으로 이미 성공한 요청의 결과 재조회에도 적용됩니다. 실행 중인 SQL을 강제로 중단하는 기능은 아니며, 실행과 취소는 같은 신원 잠금으로 순서를 정합니다.

## 5. 작은 반복 조회까지 합산하는 누적 예산

기본값은 **신원별 최근 30분 1,000회·5,000행**입니다. 운영에 적합하다고 확정한 값이 아니라 검증용 정책값입니다. 자동·일회·반복 승인 경로에 모두 적용합니다.

1. 실행 전에 요청 최대 행 수를 예약합니다. 예산이 부족하면 HTTP 429로 거부하고 SQL을 실행하지 않습니다.
2. 성공 영수증에서 실제 반환 행 수를 확인해 정산합니다. 100행을 요청해 20행을 받으면 1회·20행을 사용합니다.
3. 같은 실행 ID의 재시도와 영수증 재사용은 추가 차감하지 않습니다.
4. 응답 유실 등 결과가 불명이면 예약을 유지합니다. 30분이 지나도 미확정 예약을 자동 환급하지 않습니다.
5. 완료된 실행은 정산 시각부터 30분 창에 포함합니다. 해결되지 않은 실행은 검토자의 영수증 대조로 확인합니다.

PostgreSQL에서는 신원별 advisory lock과 요청별 잠금으로 다른 Gateway 연결 간 예약 경쟁을 직렬화합니다. 반복 승인 자체의 마지막 횟수도 같은 보호를 받습니다. 여러 연결의 감사 이벤트는 감사 체인 잠금으로 연결 순서를 보존합니다.

이 예산은 SQL 실행과 반환·예약 행 수를 계량합니다. 고유 레코드 수, 바이트, 이미 받은 정보의 재전송을 모두 계량하는 DLP 기능은 아닙니다.

## 6. 장애·정책 변경 처리

정책·카탈로그·보호 DB 대상은 정책 해시에 묶습니다. 정책을 바꾸고 재기동하면 이전 허용 요청과 범위 승인은 재사용할 수 없습니다. 서버가 소유한 역할이 바뀌어도 기존 요청과 성공 캐시의 재조회를 거부합니다.

실행 결과가 `UNKNOWN` 또는 `EXECUTING`으로 남은 경우, 보고서의 영수증 대조는 도구에 저장된 같은 실행 영수증만 읽습니다. 승인 시간이 만료되어도 대조는 가능하며 새 SQL은 실행하지 않습니다. 반환 행 본문을 검토자에게 전달하지 않고 결과 건수·영수증·감사 이력을 갱신합니다. 영수증이 없거나 일치하지 않으면 예약을 유지합니다. 이를 임의 환급하는 관리 기능은 만들지 않았습니다.

승인 대기 시간 초과는 자동 허용되지 않습니다. 위험 지표가 낮아지거나 승인 대기열이 밀려도 접근 권한을 넓히지 않습니다.

## 7. DB·API·대시보드 변경

`004_db_policy_grants.sql`은 기존 요청 테이블에 `authorization_mode`, `grant_id`, `automatic_rule_id`를 추가하고, `db_scope_grants`와 `db_query_usage`를 만듭니다. 기존 감사·업무 데이터를 지우지 않습니다. SQLite 검증 환경은 필요한 열과 테이블을 자동 추가하며, PostgreSQL은 마이그레이션을 적용합니다. 소유권이 확인된 보존형 검증 DB의 재사용 도구도 이 마이그레이션을 적용하도록 바꿨습니다.

| API | 추가·변경한 내용 |
|---|---|
| POST `/v1/db/requests` | 자동 200 / 검토 202 / 차단 403 |
| POST `/v1/db/requests/{id}/decision` | 선택적 `scope_grant` 필드 |
| GET `/v1/db/grants` | 같은 테넌트의 반복 승인·사용량 |
| POST `/v1/db/grants/{id}/revoke` | 근거를 남기는 승인 취소 |
| GET `/v1/db/budgets` | 같은 테넌트 신원별 누적 사용량 |
| POST `/v1/db/requests/{id}/reconcile` | 새 SQL 없이 불명 실행의 영수증 대조 |

왼쪽 네 메뉴와 보안 현황 차트·30분 위험 지표·초록/빨강 작동 상태·날짜별 감사·원클릭 진단은 유지했습니다. 최근 요청과 보고서에는 허용 방식을 추가했고, 승인 검토에는 반복 승인 양식·관리 목록·누적 예산을 추가했습니다. 어두운 배경·흰 글씨·청록 구분선을 유지하고 768px에서 잘리던 표를 목록으로 전환했습니다.

30분 **위험 지표**는 민감·대량·비정상 요청을 시간에 따라 감쇠하는 관제 수치입니다. **누적 예산**은 실행을 막는 실제 횟수·행 수 제한입니다. 두 수치를 혼동하지 않습니다.

PostgreSQL에서는 자동 허용 40건을 동시성 8로 사람 검토 없이 실행했습니다. 관찰 시간은 각 보고서에 남겼습니다. 두 독립 DB 연결의 기능 시험이며, 서로 다른 서버에 배포한 다중 인스턴스 시험이나 하루 전체 운영 처리량 검증이 아닙니다.

사내 DB 스키마 매핑, 기업 사용자 인증, 운영 인증서, 네트워크 격리, 운영 부하·장애 복구, 다른 Windows PC와 코드 서명은 별도 검증 대상입니다. LLM 평가는 미완료 작업이 아니라 프로젝트 범위에서 제거한 항목입니다.

## 9. 검토할 파일과 푸시 준비

실제 수정 지점은 `gateway/app/db_policy.py`, `db_access.py`, `core.py`, `main.py`, `security_agent/assessment.py`, `config/db_access.json`, 마이그레이션, 대시보드, 테스트입니다. 세부 수동 재현 명령·예상 응답·문제 해결은 [시험 설명서](../testing/TEST_GUIDE.md)에 있습니다.

실행파일·최신 보고서·화면 증거를 포함해 Git에 올릴 변경을 준비하며, 비밀번호·토큰·로컬 DB·검증 볼륨은 제외합니다. 준비 상태와 커밋·푸시 명령은 [GitHub 푸시 준비](GITHUB_PUSH_READY.md)에 기록합니다. 이번 작업에서 원격 푸시는 하지 않습니다.
