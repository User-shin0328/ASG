# Architecture

The request path is `demo-agent → Gateway → tool-sandbox`. Only the Gateway joins the agent and tool networks. The demo client cannot address the tool sandbox directly. The Gateway, tool sandbox, agent, and dashboard-to-Gateway admin path use internal Docker networks. The dashboard also joins a separate host-facing bridge so Docker Desktop can publish its UI on `127.0.0.1:18501`; the Gateway API and tool sandbox are not published to the host. The dashboard forwards a caller-supplied reviewer bearer token to the Gateway and has no embedded reviewer secret.

The Gateway authenticates opaque tokens by SHA-256 lookup and derives principal, role, task, user, and tenant from server-owned mappings. It never trusts those fields in an action request. The policy decision is separate from execution state. The Gateway persists actions, approvals, inspections, and audit entries in PostgreSQL. A restricted `gateway_app` role can update action/approval state but can only select and insert audit entries; PostgreSQL triggers also reject audit update, delete, and truncate. The demo tool service repeats task, tenant, owner, and destination checks, then atomically stores simulated side effects and an execution receipt in SQLite.

`send_report` binds approval to a canonical JSON hash of the principal, task, tool arguments, artifact content hash, and policy version. Approval expires after 15 minutes, is scoped to a reviewer tenant, and is consumed before tool execution. Repeated idempotency keys return the original action; a different request under the same key is a conflict. The tool sandbox also returns the same receipt for a repeated execution ID. Policy v2 bounds each agent to 5,000 new actions per rolling 60 seconds and five pending/approved submissions; budget checks serialize across Gateway processes and return 429 before inserting an action or creating a side effect.

PostgreSQL migrations run as a one-shot Compose service before Gateway startup. PostgreSQL advisory locks serialize matching idempotency keys across Gateway processes; approval consumption uses a row lock. Runtime checks exercised these cross-process paths, a read, reviewer approval, and approved mock-outbox submission; an attempted audit-row update was rejected by the database trigger. The SQLite adapter remains for isolated deterministic unit tests. Broader concurrency stress, database failure recovery, and the plan's full acceptance suite remain outstanding.

All sample data and report delivery are fictional and local. There is no arbitrary URL, shell, SQL, email, firewall, or external network tool. Four exploratory runs used the locally installed `qwen2.5-coder:7b` model; each unapproved `send_report` call was denied by Gateway policy. This is not a formal model evaluation. The dashboard's host-facing bridge permits outbound network connections from that container; the application currently uses it only to serve the UI and calls the Gateway over the internal admin network. Network-level egress denial for the dashboard has not been implemented or verified.
