# f30ca5c 검토의 높은 우선순위 두 항목 수정

2026-11-05. 정책 변경 시 기존 허용의 유효성 검사와 동시 요청 시험의 실패 판정을 수정했습니다. 명시적인 보안 정책으로 DB 접근을 허용·검토·차단하는 구조를 유지합니다.

이 문서는 높은 우선순위 두 항목의 수정 기록입니다. 이후 1~4번 보완도 완료했으며 최신 전체 결과와 절차는 [후속 수정 보고서](FIXES_1_TO_4.md)를 기준으로 확인합니다. 아래 통합 검사 수치는 후속 변경을 포함한 최신값입니다.

## 1. 탐지 규칙을 승인 정보에 결합

기존 정책 해시는 자유문장 탐지 패턴을 포함하지 않았습니다. 패턴만 변경하면 신규 요청은 차단되지만 같은 목적의 과거 허용 요청은 실행할 수 있었습니다.

현재 `inspection_policy_identity()`는 다음 값을 지문화합니다.

- 탐지 엔진 버전. 초기 `rules-v3`, 한국어 문맥 보완 후 현재 `rules-v4`.
- 정규화·매칭 동작 버전 `nfkc-spacing-v1` 및 Unicode 데이터 버전.
- 실제 탐지 문구 전체.
- 의도 규칙 이름·정규식 문자열·정규식 플래그.

이 정보는 DB 정책 해시와 접수 시 분석 결과에 포함됩니다. 패턴과 플래그를 바꾸면 버전 이름을 놓쳐도 정책 해시가 달라집니다. 정규화나 매칭 알고리즘 자체를 바꾸는 경우에는 `INSPECTION_NORMALIZATION_VERSION` 또는 탐지 엔진 버전을 반드시 올려야 합니다. 코드 변경을 자동으로 이해하는 해시는 아닙니다.

실행·사람 결정 시 현재 해시와 다르면 거부합니다. 과거 자동 허용, 사람 승인, 반복 업무 승인, 완료된 결과의 재조회 모두 영향을 받습니다. 새 요청에서는 과거 해시의 반복 승인을 선택하지 않습니다. 이번 배포 이전 형식의 허용도 안전하게 무효화됩니다.

이전 정책의 미실행 요청은 차단 상태로 표시하고 현재 승인 목록·대기 한도에서 제외합니다. 과거 대기 요청이 가득 차 있어도 새 정책으로 요청을 다시 접수할 수 있습니다. 기존 요청과 감사 기록은 삭제하지 않습니다.

거부 시 `DB_POLICY_REVALIDATION_DENIED` 이벤트에 판단 단계, 이전·현재 정책 해시, 현재 탐지 지문을 저장합니다. DB API는 실행에 HTTP 403 / `DB_POLICY_CHANGED`, 사람 결정에 HTTP 409 / `POLICY_CHANGED`를 반환합니다. 정책 변경 거부는 SQL 실행이나 예산 예약 전에 발생합니다.

미확정 실행의 저장된 영수증 대조는 계속 허용합니다. 대조는 이미 발생한 실행의 메타데이터와 예산을 정리할 뿐, 새 SQL이나 데이터 본문 반환을 하지 않습니다. 이를 막아 미확정 예약을 영구 방치하지 않도록 했습니다.

### 배포·기존 데이터

DB 구조 변경이나 데이터 삭제는 필요하지 않습니다. 기존 승인과 반복 승인은 새 요청·새 검토로 발급해야 합니다. 모든 게이트웨이를 같은 정책·탐지 버전으로 전환해야 하며 구버전 인스턴스를 계속 서비스하면 그 인스턴스는 이전 판단 로직을 사용합니다. 로컬 실행파일은 재빌드했습니다. 이미 실행 중인 서버에는 종료 후 새 버전 실행이 필요합니다.

## 2. 동시 요청 결과를 실제 응답으로 검증

기존 동시 요청 함수는 일반 시나리오와 별도의 접수·실행 코드를 사용해 HTTP 503도 오류가 빈 결과로 만들었습니다. 이제 두 경로가 같은 `run_scenario()` 검증을 사용합니다.

- 접수 HTTP와 상태의 조합: 200/APPROVED, 202/PENDING_APPROVAL, 403/DENIED.
- 비어 있지 않은 문자열 요청 ID와 JSON 객체 응답.
- 실행 HTTP 200, SUCCEEDED, 영수증, 0 이상의 정수 반환량.
- 통신 예외·작업자 예외를 요청별 실패로 보존.
- 접수 계약이 깨진 응답은 승인 감시기에 등록하지 않음.

정상적인 정책 차단은 통신 실패와 구분합니다. 대화형 반복 요청은 당시의 정책·대기 한도에 따라 정상적으로 차단될 수 있으므로 고정 시나리오 예상값과 다르다는 이유만으로 통신 실패로 기록하지 않습니다. 초기 5개 `--auto` 시험은 기존처럼 예상 HTTP·상태와 정상 조회 완료를 검증합니다.

콘솔에는 실패 건수와 PASS/FAIL을 출력합니다. 보고서에 `summary.total`, `summary.confirmed`, `summary.failed`를 추가했습니다. 복구하지 못한 실패가 남으면 전체 FAIL, 종료값 1입니다. 실행 응답 유실 후 실제 영수증으로 확인된 경우에는 기존 복구 흐름을 유지합니다.

## 3. 순서별 검증 방법과 예상 결과

프로젝트 루트에서 실행합니다. 전용 임시 가상 데이터만 사용하며 사내 DB 접속 정보는 필요하지 않습니다.

### 1단계: 두 수정의 회귀 검사

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_db_policy_controls tests.test_simulation_reliability -v
```

예상: 48개 모두 OK. 새 문구·플래그·정규화 버전 변경, 기존 허용·반복 승인·결과 재조회 무효화, 결정 거부의 감사 기록, 정책 변경 후 메타데이터 대조, 이전 요청의 대기 한도 제외를 확인합니다. 동시 시험에는 전체·일부 503, ID 누락, HTTP/상태 불일치, 잘못된 JSON 형태, 영수증 누락, 음수 반환량, 통신·작업자 예외, 정상 정책 차단을 포함합니다.

### 2단계: 실행파일 재빌드와 전체 인수검사

```powershell
.\scripts\build_exe.ps1
.\testing\run_tests.ps1
.\.venv\Scripts\python.exe -m testing.report_evidence
```

예상: 회귀 172개 OK, 인수 32단계 PASS, manifest VALID. 인수검사에는 별도 경로에 복사한 실행파일의 기동·실제 요청·종료가 포함됩니다. 결과는 `testing/results/latest/`와 `testing/TEST_GUIDE.md`에 기록됩니다.

### 3단계: 임시 PostgreSQL의 독립 연결 검사

Docker Desktop의 엔진이 준비된 상태에서 실행합니다.

```powershell
.\.venv\Scripts\python.exe -m testing.postgresql_checks --policy-controls
```

예상: 23단계 PASS. 두 개의 게이트웨이 연결에서 전체 예산 경쟁, 반복 승인 마지막 슬롯, 취소 반영, 규칙 변경 후 실행 거부, 독립 처리와 감사 체인을 확인합니다. 시험이 만든 임시 컨테이너만 정리합니다.

새 규칙 변경 검사의 예상값은 기존 허용·반복 승인·완료 결과 재조회 각각 403/DB_POLICY_CHANGED, 같은 목적의 신규 요청 DENIED, 추가 예산 차감 0입니다.

### 오류를 읽는 방법

- 규칙 업데이트 후 DB_POLICY_CHANGED는 재접수·재검토가 필요하다는 정상적인 거부입니다. 해시를 수동 수정하거나 기존 승인을 강제로 살리지 않습니다.
- 시뮬레이터의 HTTP 503은 정책 차단 성공이 아닙니다. 연결·서버 상태를 확인하고 보고서의 요청별 오류와 영수증을 조사합니다.
- Docker가 준비되지 않으면 PostgreSQL 검사는 FAIL 또는 실행 오류로 남겨야 합니다. SQLite 통과로 PostgreSQL 결과를 대체하지 않습니다.
