# 다음 수정 목록 1~4번: 구현과 실제 테스트 결과

2026-11-05. 요청 입력 방어, 재시작 복원, 한국어 오탐, DB 동시 처리의 네 항목을 수정했습니다. 보안 판단은 명시적인 정책과 규칙으로 수행하며 LLM을 사용하지 않습니다.

## 1. 요청 입력과 느린 연결 방어

`security_agent/http_safety.py`를 게이트웨이·도구 서비스·대시보드에서 공통 사용합니다.

- 음수·부호·비숫자·중복 Content-Length와 Transfer-Encoding 요청은 400으로 거부합니다. 지원하지 않는 chunked 본문도 수용하지 않습니다.
- 본문 상한은 게이트웨이·대시보드 24,000바이트, 도구 서비스 20,000바이트입니다. 초과는 본문을 기다리지 않고 413으로 거부합니다.
- 헤더 전체와 본문 전체에 각각 기본 3초의 제한시간을 적용합니다. 조금씩 보내며 연결을 유지하는 요청도 제한시간을 늘릴 수 없습니다.
- 헤더가 끝나기 전 제한시간 초과는 연결 종료, 본문 제한시간 초과는 408, 본문 중간 연결 종료는 400입니다.
- 서버당 처리 중 연결 수는 기본 32개로 제한하고 초과 연결은 503으로 종료합니다. 처리 중 연결이 해제되면 다시 수용합니다. 연결 제한은 모든 정상 요청의 성공을 보장하는 장치가 아니라 자원 사용 상한입니다.

실제 실행 경로와 로컬 검증 서버 모두 제한된 서버를 사용합니다. 대시보드 이미지에 공통 모듈을 포함하도록 Dockerfile도 갱신했습니다.

## 2. 재시작 후 승인 흐름 복원

`GET /v1/db/recovery?page=1`을 추가했습니다. 인증된 에이전트 자신의 테넌트·주체에 속한 미완료 요청만 50개씩 반환합니다. 날짜에 관계없이 유효한 대기·승인 요청과 미확정 실행을 조회합니다. 검토자나 다른 에이전트의 권한으로 복원을 대신할 수 없습니다.

보존 모드 시뮬레이터는 시작 시 모든 페이지를 읽어 감시기를 복원합니다.

- 대기 요청은 사람의 결정을 계속 확인합니다.
- 이미 승인된 요청은 원래 에이전트 신원으로 실행합니다.
- UNKNOWN/EXECUTING 요청은 저장된 영수증 대조를 먼저 수행합니다. 새 SQL을 발행하지 않습니다.
- 만료·정책 변경으로 무효한 대기·승인은 실행 감시에서 제외합니다. 미확정 실행은 만료 후에도 정산용 대조 대상으로 남깁니다.
- 기존 다섯 시나리오에 속하지 않는 사용자 정의 요청도 복원·보고할 수 있습니다. 보고서에 `restored`를 기록합니다.

정책·탐지 버전이 같은 상태에서의 재시작을 복원합니다. 이번 배포에서는 탐지 엔진과 보안 분석 버전이 변경되어 이전 버전의 미실행 승인은 무효화되며 새 요청·검토가 필요합니다. 기존 감사 기록은 삭제하지 않습니다.

## 3. 한국어 보안 업무 문장의 오탐 완화

자유문장에 보안 단어가 있다는 이유만으로 차단하던 일부 사례를 좁은 문맥 규칙으로 구분했습니다. 예를 들어 `보안 정책 우회 시도를 차단한 이력을 집계합니다.`는 DENIED 대신 PENDING_APPROVAL입니다.

사고·시도·차단·탐지 이력을 설명하고 조회·집계·분석·점검으로 끝나는 제한된 한국어 문장을 대상으로 합니다. 이 경우 `SECURITY_PURPOSE_REVIEW` 사유로 사람 검토를 요구합니다. 자동 허용이나 반복 승인 재사용으로 우회시키지 않습니다.

`무시하고`, `우회하여`, `비밀번호를 출력해줘` 같은 실제 명령, 설명문 뒤에 공격 지시를 붙인 혼합 문장, 영어 우회 지시와 정규화 변형은 계속 차단합니다. 열·테넌트·역할 등 명시적인 권한 위반도 계속 차단합니다.

문장 목적의 진실성을 보증하거나 모든 한국어 오탐·미탐을 해결하는 기능은 아닙니다. 이번에 확인한 정상 업무 사례를 검토 가능하게 만들면서 기존 권한 경계를 유지하는 수정입니다. 탐지 엔진은 `rules-v4`, DB 분석 엔진은 `db-security-rules-v3`이며 문맥 규칙도 승인 정책 지문에 포함됩니다.

## 4. DB 실행의 동시 처리 병목 개선

DB 조회 경로에서 전체 메타데이터 잠금은 검증·예약·정산·상태 갱신 구간에만 사용합니다. 업무 DB와 도구 응답을 기다리는 동안에는 전체 잠금을 유지하지 않습니다. 영수증 대조, 취소 대기와 진단도 긴 외부 통신이 전체 DB 요청 처리를 묶지 않도록 분리했습니다.

동일 주체의 예산과 동일 요청 실행은 키별 잠금으로 직렬화합니다. 서로 다른 주체의 조회·상태 점검은 독립적으로 진행됩니다. PostgreSQL 세션 잠금은 공용 메타데이터 연결과 분리한 최대 16개의 전용 연결 풀에서 유지합니다. 다른 스레드가 같은 세션의 잠금을 재진입해 동시성 통제를 우회하지 않도록 로컬 키 잠금도 사용합니다. 잠금·풀 대기는 10초로 제한합니다.

도구 서비스도 업무 DB 응답을 기다리는 동안 SQLite 전체 쓰기 트랜잭션을 잡지 않습니다. 대신 실행 ID의 영속적인 claim을 먼저 저장하고 조회 후 영수증을 남깁니다. 같은 실행 ID의 동시 호출은 한 번만 조회합니다. 중단된 claim에 영수증이 없다면 결과 미확정으로 남기고 SQL을 임의로 재실행하지 않습니다. 미확정 예산도 자동 환급하지 않습니다.

claim에는 요청 전체의 결합 해시가 있으며 수정·삭제 방지 트리거를 적용했습니다. 도구 서비스의 기존 SQLite DB에는 테이블을 자동 추가합니다. 보호 PostgreSQL에는 쓰기를 수행하지 않으며 별도의 PostgreSQL 스키마 변경은 없습니다.

이번 동시성 수정과 검증의 중심은 DB 조회 경로입니다. 생산 처리량이나 고가용성을 보증하는 변경으로 해석하지 않습니다.

## 5. 순서별 테스트 절차

프로젝트 루트의 PowerShell에서 실행합니다. 테스트는 별도 가상 데이터와 임시 경로를 사용합니다.

### 1단계: 집중 테스트

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_runtime_hardening -v
```

예상: 15개 모두 OK.

| 검사 | 예상 결과 |
|---|---|
| 세 서비스의 잘못된 길이·중복 길이·전송 방식 | 400, 요청 실행 안 됨 |
| 초과 본문 | 본문을 기다리지 않고 413 |
| 느린 본문·느린 헤더 | 제한시간 내 408 또는 연결 종료 |
| 제한된 서버 용량과 회복 | 초과 연결 503, 기존 연결 종료 후 정상 요청 200 |
| 정상 보안 업무 목적 네 문장 | 모두 검토 대기, 자동 허용 아님 |
| 실제·혼합·변형 공격 지시 일곱 문장 | 모두 차단 |
| 설명문에 열·테넌트 위반 포함 | 명시적 위반은 차단 유지 |
| 같은 가상 DB에서 재시작 | 대기·승인·미확정 네 요청 복원, 다른 주체 요청 제외 |
| 복원 후 승인·조회·영수증 대조 | 영수증 4개, 사용 4회·15행, 이중 조회·차감 없음 |
| 복원 페이지 처리 | 55건 모두 복원, 검토자 호출은 403 |
| 만료·미확정 요청 복원 | 만료된 허용은 제외, UNKNOWN은 유지 |
| 느린 업무 조회와 다른 주체·상태 점검 | 지연을 풀기 전에 다른 조회와 상태 점검 완료 |
| 같은 요청 8개 동시 실행 | SQL 1회, 예산 1회 차감 |
| 조회 도중 중단된 claim의 재시도 | 조회 함수 재실행 없음, UNKNOWN·예약 유지 |

원시 결과는 전체 회귀 로그에도 포함됩니다. 제한시간 테스트는 시험 서버에서 0.3초로 줄여 수행하며 제품 기본값은 3초입니다.

### 2단계: 실제 PostgreSQL 검증

Docker Desktop을 시작하고 `docker info`가 정상 응답하는지 확인합니다.

```powershell
.\.venv\Scripts\python.exe -m testing.postgresql_checks --policy-controls
```

예상: 임시 PostgreSQL 23단계 PASS. 두 게이트웨이 연결의 예산 경쟁, 반복 승인 마지막 사용, 규칙 변경, 감사 체인을 확인합니다. 추가로 첫 조회에 지연을 주입하고, 지연 해제 전에 다른 주체의 실제 조회와 readiness 검사가 완료되는지 검사합니다.

자신이 만든 임시 컨테이너만 정리합니다. 기존 보존형 DB나 사내 DB를 대상으로 하지 않습니다. Docker 미기동은 코드 통과로 간주하지 않고 실행 오류로 기록해야 합니다.

### 3단계: 실행파일 재빌드·전체 검증

```powershell
.\scripts\build_exe.ps1
.\testing\run_tests.ps1
.\.venv\Scripts\python.exe -m testing.report_evidence
```

예상: 전체 회귀 172개 OK, 로컬 HTTP·독립 EXE 인수검사 32단계 PASS, manifest VALID. 실제 시험한 소스 지문과 ASG.exe 해시가 보고서에 결합됩니다.

### 4단계: 재시작 흐름 수동 확인

```powershell
.\.venv\Scripts\python.exe -m tests.virtual_agent_simulation --persist-data
```

1. 민감정보 요청을 만들고 승인 대기 상태를 확인합니다.
2. 콘솔의 0번으로 종료합니다. DB 디렉터리는 보존됩니다.
3. 같은 명령으로 다시 실행하고 보존 요청 복원 건수를 확인합니다.
4. 이전 요청을 사람 승인하면 시뮬레이터가 원래 주체로 실행해야 합니다.
5. 감사 기록에서 기존 요청 ID·새 실행 결과·영수증을 확인합니다. 같은 요청의 재조회로 예산이 추가 차감되면 실패입니다.

버전 변경으로 무효화된 요청은 새로 접수해야 합니다. 영수증 없는 중단 실행은 확인 필요 상태로 유지하는 것이 정상입니다.
